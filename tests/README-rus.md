# Тесты и эталон методики

> На английском: [`README.md`](README.md)

## Зачем

Файлы в `data/` — **зафиксированное поведение авторской методики**. Они существуют
для того, чтобы любое изменение кода, которое меняет численные результаты, было
замечено сразу, а не через несколько месяцев в статье.

## Как запускать

```bash
pip install -e ".[dev]"     # один раз
pytest                       # весь набор
pytest tests/test_golden.py  # только regression-фикстуры
```

Настройки pytest лежат в `pyproject.toml`, правки `sys.path` не нужны:
пакет установлен, и тесты импортируют его так же, как пользователь.

## Как устроено

| Файл | Роль |
|---|---|
| `synthetic.py` | детерминированные синтетические записи (фиксированный seed) |
| `golden.py` | единое описание того, что фиксируется: набор случаев + ввод/вывод CSV + сравнение |
| `generate_golden.py` | перегенерация фикстур: `python -m tests.generate_golden [случай ...]` |
| `test_golden.py` | regression-проверка всех случаев + согласие ускоренной ветки на конвейере |
| `test_numba_parity.py` | пункт N-1: numba-ветки обязаны быть точными копиями python-веток |
| `data/meta.json` | окружение, ветка и коммит, при которых снят эталон |

Реальные записи испытуемых в репозиторий не попадают: все записи генерируются
из `synthetic.py`.

## Дисциплина изменений

1. Меняешь код → запускаешь проверки.
2. Проверки упали → решаешь, **осознанное** ли это изменение методики.
3. Если да: описываешь в `CHANGELOG.md` с пометкой «меняет численные результаты»
   и только тогда перегенерируешь фикстуры командой
   `python -m tests.generate_golden <случай>`.
4. Если нет — это регресс, фикстуры не трогаешь.

## Эталон снимается на python-ветке

Фикстуры генерируются и проверяются внутри `golden.reference_branches()`, то есть
всегда на python-ветках — они объявлены эталоном методики (пункт N-1).

Причина: ускоренные ветки алгоритмически совпадают с python-ветками, но не
бит-в-бит. `_ols_core_numba` суммирует циклом, а numpy — попарно, поэтому наклон
и p-value тренда расходятся в последних битах (замерено: до 1.0e-14). Если снимать
эталон на ускоренной ветке, фикстуры перестают проверять методику и начинают
зависеть от того, установлена ли numba и какая версия LLVM у неё внутри.

Что numba **не** должна менять — решения методики. Это проверяется двумя уровнями:

* `test_numba_parity.py` — отдельные функции, с допуском;
* `test_golden.py::test_numba_does_not_change_markup` — полный конвейер: набор
  событий, границы и длительности обязаны совпасть точно.

## Два уровня сравнения

Бит-в-бит воспроизводимость достижима только внутри одного окружения, поэтому
сравнение двухуровневое.

**Всегда** (`test_case_matches_golden`):

| Что | Как сравнивается |
|---|---|
| схема, число строк, позиции NaN | точно |
| целочисленные столбцы | точно |
| решения методики: `t_start*`, `t_end*`, `duration*`, `i_*`, `n_*`, `index`, `count` | точно |
| непрерывные величины | допуск `rtol=1e-9`, `atol=1e-12` |

**В окружении эталона** (`test_case_matches_golden_bit_exact`, пропускается, если
версии numpy/pandas/scipy отличаются от записанных в `meta.json`): всё точно,
до последнего бита.

Почему нельзя требовать бит-в-бит всегда: numpy 2.x считает тригонометрию другими
SIMD-ядрами, чем 1.24, поэтому на заявленном минимуме зависимостей (`numpy>=1.24`)
эксцентриситет и скорость расходятся в последних битах — замерено до 1.3e-11 при
значениях в сотни град/с, то есть ~1e-14 относительно. Разметка при этом
не меняется ни в одном случае.

### Отдельный допуск для sigmoid-ветки

`sigmoid_90hz` и `sigmoid_250hz` сравниваются с `rtol=1e-5` и без точного
сравнения границ (`golden.TOLERANCES`). Это единственная ветка, где событие
описывается не порогом, а фитом: `curve_fit` подгоняет логистическую кривую,
а границы события вычисляются из её параметров. Между scipy 1.10 и 1.17 параметр
наклона `k` расходится на 2.3e-7 относительно, границы события — на 5 нс при шаге
отсчётов 11 мс.

Цена: для sigmoid-случаев regression-тест грубее, и мелкий дрейф поймает только
бит-в-бит проверка в окружении эталона. Это следствие того, что результат ветки
наследует точность оптимизатора, а не свойство самой методики.

## Матрица CI

`.github/workflows/ci.yml` гоняет набор по матрице {numba есть / нет} ×
Python 3.10–3.12. Колонка без numba — полноценная проверка методики: эталон снят
именно на python-ветках. Отдельный шаг проверяет, что колонка настоящая: если
установка numba провалилась, две колонки стали бы одной, и расхождение веток
снова прошло бы незамеченным.

## Точность записи фикстур

Фикстуры пишутся с `float_format="%.17g"` и читаются с
`float_precision="round_trip"`. Без `round_trip` быстрый парсер pandas округляет
с относительной погрешностью ~1e-16, и точное сравнение ломается.
